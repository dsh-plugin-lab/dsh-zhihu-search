# 决策：声明面下限抬到 RC 线起点（2026-10-10）

状态：生效

## 问题

issue [#2](https://github.com/zlZayn/dsh-zhihu-search/issues/2)（compat 巡检 2026-10-05 那轮红了）有两个独立根因，
本篇记第一个：**声明面罩不住承诺线**。

当时的 `declaration` 作业输出：18 条 `@deepseek-ai/dsh-*` 声明「最新可取 `0.1.7-rc.2`，
而 `next` = `0.2.0-rc.2`」—— 即声明面根本达不到承诺线。

## 事实（本轮现查与实测，不抄进文档）

1. **npm 的预发布语义是根因**：候选带预发布段时，区间里必须有一个 `major.minor.patch`
   **相同且也带预发布段**的比较子才允许匹配。旧下限 `>=0.1.7-alpha.1` 的元组是 `(0,1,7)`，
   候选 `0.2.0-rc.2` 是 `(0,2,0)` —— 永远对不上，**与上界写成什么无关**。
   实测：`node scripts/check-declaration.mjs` 报「28 of 28 declared ranges do not cover the next line」。
2. **承诺线早已迁到 `next`（2026-09-24），下限没跟着走** —— 那一批改动只放了上界（`<0.2.0` → `<0.3.0`），
   当时的判断是「区间本就罩得住 rc 线」。那个判断**是错的**，本篇把它反转。
3. **README 与 ARCHITECTURE 有两处陈述与事实不符**：`README` 的「前置」写着一条与 `engines.dsh`
   不一致的区间字面量；`docs/ARCHITECTURE.md` 的「驱动版本用 dist-tag」还称 `alpha` 是承诺线。
   两处都一并改对（顺带把那两个字面量换成指向 `package.json` 的指针 —— 它会漂）。
4. **抬到 `>=0.2.0-rc.1 <0.3.0` 后本机实测全绿**：`npm install`（清掉旧锁与旧树之后）解析出的树
   全部落在 RC 线上，`npm run typecheck` 与 `npm test` 零错误。锁文件按官方源重生成。
5. **换线验证链**：`node scripts/compat-swap.mjs swap next`（在一次性副本里）跑完
   「改写 → 清锁清树 → 装 → 核对」，18 个包与宿主本体全部落在目标线上，其后 typecheck 与
   全套测试同样零错误。

## 决策

1. `engines.dsh` 与全部 27 条 `@deepseek-ai/dsh-*` 声明（9 条 peer + 18 条 dev）→
   **`>=0.2.0-rc.1 <0.3.0`**（28 处同改）。
2. 取**那条线的起点**而不是它当前指向的那一版：同一 `major.minor.patch` 内的后续预发布都罩得住
   （实测 `>=0.2.0-rc.1` 罩得住 `0.2.0-rc.2`），而取当前版会把下限锁死在一次周更的观测上。
3. **上界保留 `<0.3.0`**：本仓既定策略是「上界排除下一个大版本」，本次沿该策略执行。
4. README / README_en 的「前置」与「版本兼容」改指真源，不再抄值；承诺线一律写 `next`。
5. **档位：minor**（维护者裁定）。Q0 是（声明在产物里）；Q1 否（旧宿主上插件照常运行，
   只是不再承诺那条线）；Q2 **是** —— 落在 alpha 线的使用者必须升宿主才能继续用新版本。
   按本仓问题链「Q2 是 → major」会卡在人类确认上，而维护者明确裁定按 minor 走；
   这是本条**唯一**偏离问题链默认的地方，理由就是「只缩窄承诺面、没有任何用法失效」。

## 替代方案（试过，为什么不选）

- **保持下限、只把上界放宽到 `<0.3.0`**（2026-09-28 那次就是这么做的）：不解决问题 ——
  拦住匹配的不是上界，是预发布元组。实测声明面照样全红。
- **下限写成能同时罩住 alpha 线与 RC 线的并集**（`>=0.1.7-alpha.1 <0.2.0 || >=0.2.0-rc.1`）：
  不选 —— 那等于**仍然承诺 alpha 线**，与「承诺线在 RC 线」矛盾；而且 `compat-swap.mjs` 的保形换版
  只认「运算符 + 版本号（可选上界）」这种形状，`||` 会被它判成不认识的形状而报错停下。
- **改判据而不是改声明**（让 `check-declaration` 放宽成「能取到任意一个 >= 下限的版本就算过」）：
  不选 —— 那是在给一条**确实罩不住**的声明面开绿灯。使用者按那个区间装出来的宿主装不到我们要的线。
- **把承诺线改回 alpha**：不选 —— alpha 线上的版本不在我们声明的区间里，改回去等于把使用者引到
  我们测不了的那条线上；而且 2026-09-24 那次迁线的结论（承诺线跟着宿主实际在跑的那条走）没有新证据推翻。

## 影响

- **使用者侧可观察变化**：落在 alpha 线的使用者必须升宿主到 `next` 线（README 已把安装命令写明）。
  这是定档时的关键事实，按 Q2 记在本次 minor 上。
- **声明在产物里，因此本次必须发版**（`package.json` 随包发布）。
- **同一条预发布语义的固有代价**：宿主再往前推一个补丁位的预发布时，这条下限会再次罩不住，
  届时要再抬一次 —— 这不是形状选错，是「跟预发布线」这件事本身的代价。
- 换版脚本那条链的修复（`engines.dsh` 同进同退、清旧线残留、自带核对）另记 →
  [2026-10-10-swap-must-move-engines-dsh.md](2026-10-10-swap-must-move-engines-dsh.md)。
